> New to this project? Read `HANDOFF.md` first: what it is, why it's built this way, what's verified, and what to do next.

## Non-negotiables

1. **Page content is WordPress block markup.** `Page.content`, `Site.header` and `Site.footer` are serialized Gutenberg markup. Never store HTML that didn't come from `serialize()`.
2. **Never hand-write block markup.** Build `BlockNode` trees and go through `normalizeSections()/normalizeBlocks()` → `toMarkup()`. This includes templates (`wp/templates.ts`).
3. **Zero invalid blocks.** Every change must keep `npm test` green. The tests run WordPress's own block validator over every pattern in every tone, the demo site, header/footer, templates and the export.
4. **Use preset slugs, never raw values,** for colors, font sizes and spacing in patterns and prompts. Raw values break restyling and the Site Editor experience.
5. **Core blocks + site-defined `prepress/*` blocks only.** Custom blocks are dynamic (attributes in the comment, HTML from a sanitized mini-mustache template), defined as `CustomBlockDef` in `site.blocks`, rendered by `fillTemplate()` and exported inside the theme or, by choice per export, a companion `<site>-blocks` plugin (`blocks/<slug>/block.json` + `render.php` + `assets/prepress-blocks.js`; `exportSite(site, { blocks })`). The TS renderer, the exported editor JS (`RUNTIME` in `wp/wpBlocks.ts`) and the generated PHP must stay identical; `tests/customBlocks.test.ts` checks all three (PHP part needs a local `php`). Never add a static custom block or one that needs a plugin.
7. **Follow the theme system (`docs/THEME-SYSTEM.md`).** Which block: core block settings → core block + a block style (`site.blockStyles`, `is-style-<set>-<name>`) → a pattern of core blocks → a custom block only when it's `kind` art, interactive or an effect wrapper (whose text is inner blocks). CSS has five homes (tokens, theme.json element/block defaults, block styles, custom-block CSS, a small site CSS); no `className` except a registered `is-style-*`, no raw colours/fonts/radii (`var(--wp--custom--radius--*)` follows the Design). `lintSet()` must report nothing for library sets; MCP `validate_site` reports `lintSite()` warnings. MCP `get_guidelines` serves the doc to AI clients.
6. **WordPress version is pinned** (`TARGET_WP_VERSION` + `overrides` in package.json). When bumping: update every `@wordpress/*` override to the new `wp-X.Y` dist-tag, set the direct deps to the same exact versions, run tests, check for attribute moves (WP 7.0 moved heading/paragraph `textAlign` into `style.typography.textAlign`).

## Commands

- `npm test` — vitest (jsdom). ~30 s; WordPress packages are inlined via `test.server.deps.inline`.
- `npm run dev` — Vite + the real server handler (`server/app.ts`): site at `/`, editor at `/?admin=1`, data in `./prepress-data` (or `PREPRESS_DATA`).
- `npm run build` — single-file admin build (`dist/index.html`) + `dist/prepress.html` artifact page.
- `npm run build:bin` — build + compile `bin/prepress` (Bun, embeds `dist/index.html`). `build:bin:all` cross-compiles macOS/Linux/Windows.
- `npx tsc` — typecheck.
- `npm run build` also bundles the headless engine (`src/lib/engine.ts` → `dist/engine/engine.js`, Vite SSR, everything inlined) that the server uses for MCP, publish and export.

## Gotchas

- The server runs the same lib as the editor (`src/lib/engine.ts`) under a **jsdom** shim (`server/dom.ts`). Not happy-dom: WordPress's attribute parser (hpq) needs `hasOwnProperty(el.attributes, name)`, which happy-dom lacks, and images lose `src`/`alt`. Bun can't bundle `createRequire(import.meta.url)('x.json')` (css-tree, via jsdom): `scripts/compile.ts` rewrites those into static imports. It also inlines `fs.readFileSync(path.resolve(__dirname, …))` data files (jsdom's default stylesheet) and stubs sibling `require.resolve('./…')`: both work on the build machine (absolute node_modules paths) and crash the binary everywhere else. Smoke-test a release binary with `node_modules` moved away.
- The draft (`<data>/draft.json`) has a `rev`; every writer goes through `server/store.ts`. Editor saves send `baseRev` and get 409 on conflict; MCP writes broadcast on `/api/events` and open editors reload.
- Register site blocks (`registerCustomBlocks(site.blocks)`) before parsing/serializing content that uses them — App, MCP tools and `exportSite` all do.
- AI-supplied text that ends up in PHP/CSS comments (site name, block/pattern titles) must go through `comment()` in `wp/wpBlocks.ts`; templates through `sanitizeTemplate`, CSS through `sanitizeCss`.

- The editor is the real `@wordpress/block-editor` (`src/ui/editor/Editor.tsx`). Its `onChange`/`onInput` go through `serialize()`, so rule 1 holds. `__experimentalFeatures` must have presets keyed by origin (`{ theme: [...] }`) and `appearanceTools` expanded by hand (PHP does that in WordPress).
- Page editing shows header + content + footer in one canvas (site-editor style, `src/ui/editor/templateAreas.tsx`): three editor-only `prepress-editor/area` wrapper blocks, root `templateLock: 'all'`. They are never stored: `splitAreas()` serializes each area's inner blocks back to `page.content` / `site.header` / `site.footer`, and only areas whose output changed are written (so opening a page never marks a part custom). Toggle: status bar "Hide header & footer" (localStorage).
- Keep `EditorProvider` settings referentially stable (memoized assets, no fresh `[]` props): a new `__unstableResolvedAssets` reloads the canvas iframe and drops keystrokes.
- Header/footer are editable (top-bar tabs). `site.custom[part]` marks a hand-edited part: `rebuildParts()` then keeps it and only syncs menu links (`syncPartLinks`); untouched parts are still regenerated. Pass the previous page list to `rebuildParts(site, before)` from any page add/rename/remove.
- Core edit components for `site-title`, `site-tagline`, `navigation`, `navigation-link` need core-data/REST, so `src/ui/editor/dynamicBlocks.tsx` replaces them via `editor.BlockEdit`. Attributes stay core's.
- Canvas CSS is passed to the editor iframe via `__unstableResolvedAssets.styles`; parent-page CSS is not the content CSS.
- The public site is static HTML rendered by the admin (`renderPage`) at Publish time and written by the server into `--out` (a plain static folder any web server can serve; Prepress needn't run). Publish only touches files in its manifest (`<data>/published.json`) and backs up anything else it would overwrite. `--out` may never contain `--data`. Changing `render.ts` needs a re-publish to show up.
- Toolbar: **Publish** opens `PublishDialog` (tick targets → `POST /api/publish {targets}`; with none, the connection form first). The gear opens `SettingsDialog` (Site: title/tagline/brief · Publishing: `DeployPanel` · AI connection: `McpPanel` · Data); the PanelRight icon toggles the sidebar. Sidebar tabs: Page · Block · Styles · Pages (pages, site blocks, patterns).
- The editor has no built-in AI (no AI tab, no /api/claude, no ANTHROPIC_API_KEY): all AI editing goes through MCP. `ServerOptions.runtime` ('desktop' when `PREPRESS_APP=desktop`, set by the Tauri app) picks what Settings → AI connection offers: desktop → stdio command/config only and HTTP /mcp disabled; server → HTTP /mcp + token only. `src/lib/ai/*` remains for the offline sample site (demo) and the tests.
- One-click AI app setup (`server/clients.ts`, desktop runtime only, `POST /api/mcp/clients {id, action}`): surgical edits of each app's MCP config (JSON `mcpServers`/`servers`, Codex TOML table, Hermes YAML map), first-change backup `<file>.before-prepress`, JSON files with comments are refused (shown as "set up by hand"). Paths per OS are in `CLIENTS`; `tests/clients.test.ts` checks every format round-trips and undo restores the file. Never write to a user's config without that user clicking Connect.
- External media → library (`server/media.ts` + `src/lib/wp/media.ts`): `MEDIA_ATTRS` (+ custom blocks' `image` attributes) are scanned; the server downloads (public addresses only, re-checked on every redirect; magic-byte type check; no SVG), dedupes by content hash, and blocks are re-serialized with the local URL. MCP `change()` downloads *before* taking the draft lock, then applies the same change with the URL map. The editor's `MediaLocalizer` (Editor.tsx) does the same via `POST /api/media/import`. The normalizer accepts `/uploads/<file>` image URLs.
- `view_page` (MCP): `server/screenshot.ts` renders the draft with `renderPage(..., {markSections: true})`, serves it on a throwaway 127.0.0.1 port, and drives a headless Chromium over `--remote-debugging-pipe` (no debugging port). Sections are clipped by `data-pp-section`.
- Free hosting: `hosting/` is a separate service (built with `npm run build:hosting`, deployed by `deploy/hosting/deploy.sh` to 95.217.217.146; secrets only in the server's `/etc/prepress-hosting.env`). Names/tokens in `<HOSTING_DATA>/sites.json` (token SHA-256 only); presigned PUTs pin content-type/length/cache-control. Client: `server/targets/prepress.ts` (`prepress://name`, token in `<data>/hosting-token`). Shared name rules: `hosting/names.ts`. Caddy gotcha: two `rewrite`s in one block are mutually exclusive — the Caddyfile uses `uri path_regexp` + one `rewrite`; inline path matchers must start with `/` (`*/` is not a matcher).
- Library: `hosting/library.ts` (API + storage in `<HOSTING_DATA>/library/`), `hosting/pages.ts` (homepage + library pages, server-rendered, everything escaped, CSP), previews served with a `sandbox` CSP. Prepress side: `src/lib/library.ts` (share builders + `importLibraryItem`, which re-normalizes everything), `server/library.ts` (client; adds the site token), `src/ui/LibraryDialog.tsx`, MCP `library_*` tools. Items may carry `uses` (ids they're built from → "Built with" / "Used in" on item pages) and a moderator-only `official` flag ("By Prepress"; reports can't hide official items).
- Official library sets live in `library-sets/<set>/` (style → `prepress/<set>-*` blocks → patterns → template, plain data). `buildLibrarySet()` (`src/lib/librarySets.ts`) builds the site + library drafts with lineage; `tests/librarySets.test.ts` checks zero repairs/invalid blocks and that every layer is used. Visual QA: `npm run build && npx bun scripts/qa-set.ts <set> <out>`; publish: `npx bun scripts/seed-library.ts <set> --target local|prod` (idempotent; prod ids in `library-sets/<set>/published.json`, owner token in `~/.config/prepress/official-token`, admin token read over SSH, never stored). Sets are built with `library-sets/kit.ts` and follow `docs/THEME-SYSTEM.md` (`lintSet` in the tests): looks are block styles in the set's `blockStyles`, custom blocks carry `kind`, patterns carry a `role`; block CSS is unscoped, so scope it to `.wp-block-prepress-<slug>` / the set `prefix` (`.kx-*`). Register new sets in `library-sets/index.ts`. Section padding only goes up to `var:preset|spacing|80`. Block attributes can't use reserved names (`style`, `align`, `className`, …). Dark styles work as-is (base dark, contrast light); add `color-scheme: dark` in the style's CSS.
- Sticky header: `Design.stickyHeader` (optional, off for older designs; Styles panel checkbox, MCP `set_design`). `buildThemeJson` appends `STICKY_HEADER_CSS` after any theme.json patch, so it lands in the export too. Other sticky things offset by `top: calc(var(--pp-header-h, 0px) + …)`; a style whose header isn't ~92px tall sets `:root{--pp-header-size:…}`.
- CSS-only controls in blocks: put the hidden `<input>` *inside* its `<label>` and drive state with `:has()`. A hidden input elsewhere in a tall block gets focused on click and the browser scrolls to it (the page "jumps"). Anything that can poke past the viewport (rotating shapes, glows) needs `overflow:clip` on the block or `.wp-site-blocks{overflow-x:clip}` in the style; clip, not hidden, so sticky keeps working.
- Set photography: library-set pictures live in the bucket under `_library/<demo>/` (immutable cache: a changed picture needs a new file name) and are referenced by absolute URL; importing a template copies them into the site's media library. Generated stock images: `node scripts/gen-image.mjs <out.png> <aspect> "<prompt>"` (Gemini, key in `~/.config/prepress/gemini-key`). Write "no text, no logos" into every prompt, never show a real brand, and say in the template brief that the photos are generated samples. Don't put `loading="lazy"` on above-the-fold images in block templates (it also hides them from `qa-set.ts` screenshots).
- Fonts have three slots: `headingFont`, `bodyFont` and optional `monoFont` (FONTS entries with `mono: true`; default `system-mono`). theme.json always has the `mono` family, so blocks may use `var(--wp--preset--font-family--mono)`.
- Rich-text attributes are sanitized in the normalizer (`src/lib/wp/inline.ts`): only editor-style inline HTML survives (AI output and library items are untrusted). Don't bypass `normalizeSections` for content from outside.
- Desktop app: no `on_navigation` guard — wry calls it for iframes too (embeds, library previews) without telling the frame. External links open via `on_new_window`.
- MCP has two transports over one tool set (`mcpServerFactory` in `server/mcp.ts`): HTTP `/mcp` on the editor server, and stdio `prepress mcp --data …` (`server/stdio.ts`). Both use `createSiteCore()` (`server/app.ts`: store, publish, deploy, export without HTTP). An editor server and a stdio process may share one data folder: `DraftStore` writes take `<data>/draft.lock`, publish/deploy take `<data>/publish.lock`, and `store.watch()` polls `draft.json` so the server's SSE announces writes from the other process. In stdio mode stdout is JSON-RPC only: `server/stdio-guard.ts` (imported first) sends `console.log` to stderr.
- Publish targets (`server/deploy.ts`, transports in `server/targets/`) upload `--out` after Publish. A target is a connection string (`targets/connection.ts`): `sftp://` (ssh2, pure JS: password, agent or key; host key pinned per target in `<data>/deploys/<id>.json`), `ftp://`/`ftps://` (basic-ftp), `s3://` (own SigV4 in `targets/s3.ts`, tested against AWS's published examples; `?endpoint=` for R2/MinIO), or a folder. Same ownership rule per target: hash manifest, never delete what we didn't upload, back up what we'd overwrite. Secrets live only in `<data>/deploy.json` (0600): every view/API/MCP response uses `viewTarget()` (masked `••••••`), and MASK sent back means "keep the stored secret". Never return a raw `DeployTarget` to the client or MCP.
- No password, by design (local app). The server listens on 127.0.0.1 only and `createHandler` answers 421 unless the `Host` header is a loopback name (DNS-rebinding guard), plus the Origin check on writes. Don't add `--host`/0.0.0.0 back without real auth.
- Desktop app: `desktop/` (Tauri 2). `src-tauri/src/main.rs` spawns the bundled `prepress` (sidecar, `externalBin`) per site folder on a stable per-folder port with `PREPRESS_PARENT_PID`, and loads `/?admin=1`; `ui/` is the launcher (recent sites, create, open folder). `Info.plist` allows local networking (ATS), otherwise WKWebView won't load http://127.0.0.1. The window uses `.disable_drag_drop_handler()`: Tauri's file-drop handler otherwise swallows every drag on macOS/Windows and the block editor's drag & drop does nothing. Build: `npm run build:desktop` (copies `bin/prepress` to `binaries/prepress-<triple>`). Release on macOS: `APPLE_SIGNING_IDENTITY="Developer ID Application: …" PREPRESS_NOTARY_PROFILE=prepress-notary npm run build:desktop` signs (hardened runtime + `Entitlements.plist`: Bun's JIT needs allow-jit/unsigned-executable-memory), notarizes and staples the .dmg. Unsigned/ad-hoc builds show "is damaged" on other Macs. Auto-update: `tauri-plugin-updater` checks `plugins.updater.endpoints` (`_downloads/latest.json` in the bucket) 8 s after start, every 6 h and from "Check for Updates…" (app menu; Help elsewhere), asks, downloads, verifies the minisign signature, replaces the app and restarts (servers stopped first). The build signs the updater bundle with `~/.config/prepress/updater.key` (public key in `tauri.conf.json`; lose the private key and installed apps can't update), staples the app and writes `bundle/latest.json`; `PREPRESS_S3_ACCESS_KEY=… PREPRESS_S3_SECRET_KEY=… npx bun scripts/release-desktop.ts` uploads tarball, dmg, then latest.json. Bump the version in package.json, package-lock.json, tauri.conf.json, Cargo.toml and server/version.ts: the updater only moves to a higher version.
- Block styles (`src/lib/wp/blockStyles.ts`): one `BlockStyleDef` feeds the preview/editor CSS (`compileBlockStyles`: `styles` → `:root :where(<sel>.is-style-x)`, `css` flattened by `nestCss` — `&`, descendants, `@media`), the editor's Styles picker (`registerBlockStyles`) and the export (`inc/block-styles.php`: `register_block_style` with `style_data` + `inline_style`). Selectors come from block.json `selectors.root` (`styleSelector`: button → `.wp-block-button.is-style-x .wp-block-button__link`). theme.json per-block `css` is compiled exactly like WordPress (`wpBlockCss`: declarations + one level of `&`, no `@media` — `isWpBlockCss`).
- `@wordpress/format-library` CSS is not in its `exports` map; it's aliased in `vite.config.ts`.
- `@wordpress/vips/worker` is aliased to `src/stubs/vips.ts`; otherwise 13 MB of WASM gets bundled.
- `@wordpress/*` direct dependencies must equal their override versions exactly or npm errors with `EOVERRIDE`.
- Dynamic blocks (site-title, navigation, post-content, template-part) save as self-closing comments; `wp/render.ts` renders them for the preview. If you add a dynamic block to a template or part, add a renderer case.
- Layout classes and container CSS are added at render time (like PHP `wp_render_layout_support_flag`), not saved in markup. Don't put `is-layout-*` classes into content.
- Placeholder images are SVG data URIs; `applyDesign()` regenerates them from `alt` text in the new palette.
- AI JSON is untrusted: unknown blocks and attributes are dropped and reported, not passed through.

## Adding a pattern

1. Add an entry to `PATTERNS` in `wp/patterns.ts` (description + compact props schema the model sees + `build`).
2. Use `section()`, `card()`, `grid()`, `buttons()` helpers and preset slugs.
3. Add sample props to the "every pattern" test in `tests/roundtrip.test.ts` if it needs new keys; run `npm test`.

## Adding a starter template

1. Add an entry to `STARTERS` in `src/lib/starters.ts`: `plan` (name, tagline, design with preset fonts/palette, pages) and `pages` (pattern calls per page slug, same shape as AI output). Write `{name}` wherever the site name belongs; link only to the starter's own pages.
2. Write a `brief` the AI can act on: kind of site, tone, what visitors should do.
3. `npm test` — `tests/starters.test.ts` checks every starter: valid blocks, no normalizer repairs, name filled in, no dead internal links.

## Adding to a library set

1. A look a core block can't express in its settings → a block style in the set's `blockStyles` (`blockStyle(set, slug, label, types, { styles, css })` from `library-sets/kit.ts`), used as `className: is('<set>-<slug>')`.
2. A record (menu line, hours, byline, stat) → core blocks + block styles inside the pattern, never a custom block.
3. A custom block only for art / interactive / effect (`kind`); an effect's text is inner blocks (`{{{content}}}`).
4. A pattern = one `section()` with a `role`; add it to `template.ts` pages by key.
5. `npm test` (`lintSet` must be empty), then `npm run build && npx bun scripts/qa-set.ts <set> <out>` and look at desktop + phone.
