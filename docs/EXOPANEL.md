# Running Prepress inside Exopanel

How to provision Prepress as the site builder for an Exopanel-hosted site.

## Model

One Prepress process per site. It is the **editor**, not the web server:

```
                     https://example.com  ──▶ panel web server (nginx/Apache, TLS)
                                                │  serves static files only
                                                ▼
 https://edit.example.com ─▶ proxy ─▶ prepress :81xx ──Publish──▶ /home/acme/htdocs/example.com
        (editor + /mcp)                 │                          (--out = site docroot)
                                        └─ /home/acme/prepress/example.com  (--data, private)
```

- **Publish** writes plain HTML + media into the site's document root. The live
  site needs no PHP, no database and no running Prepress.
- The Prepress process only has to run while someone edits (or while an AI client
  uses `/mcp`). The panel can start it on demand and stop it afterwards
  (idle it uses about 160 MB of RAM).
- Everything Prepress knows about a site lives in its `--data` folder. Back that up
  and you have the site.

## 1. Build and install the binary

Build host needs Node 20+ (Bun is fetched by `npx`):

```bash
git clone git@github.com:digitalnodecom/prepress.git && cd prepress
npm ci
npm test                  # optional, ~30 s
npm run build:bin:all     # → bin/prepress-linux-x64, bin/prepress-linux-arm64, macOS, Windows
```

Install on each panel server (one shared binary, about 100 MB, no runtime dependencies):

```bash
install -m 0755 bin/prepress-linux-x64 /usr/local/bin/prepress
prepress --version
```

Requirements on the server: glibc Linux (x64 or arm64), and OpenSSH's `sftp`
client only if users add SFTP deploy targets.

## 2. Per-site layout

| What | Example | Notes |
|---|---|---|
| System user | `acme` | The site's existing panel user. Prepress runs as this user so published files get the right owner. |
| Document root (`--out`) | `/home/acme/htdocs/example.com` | The panel's static vhost root. |
| Data folder (`--data`) | `/home/acme/prepress/example.com` | Mode `0700`. **Must be outside the docroot.** Prepress refuses to start if `--out` contains it. |
| Editor port | `127.0.0.1:8101` | Unique per site, allocated and stored by the panel. Never bind `0.0.0.0`. |
| Editor hostname | `edit.example.com` (or `<site-id>.edit.<panel-domain>`) | Must be the **root** of a hostname: the editor, `/api/*` and `/mcp` don't work under a path prefix. |

What Prepress writes into `--data`:

```
draft.json            current site (pages, header/footer, design, custom blocks)
published.json        what the last Publish wrote (ownership manifest for --out)
uploads/              media library
admin-password.txt    only if no password was given (0600)
mcp-token.txt         MCP bearer token if none was given (0600)
sessions.json         hashed login sessions
deploy.json, deploys/ deploy targets and their state
backup/               files Publish/deploy replaced that it hadn't written
exports/              WordPress export zips
```

Publish only replaces or removes files listed in its manifest. Panel files in the
docroot (`.htaccess`, `.well-known/`, `.user.ini`) are left alone. The panel's
placeholder `index.html` is copied to `<data>/backup/` before the first Publish
overwrites it.

## 3. Configuration (env file)

Pass settings through the environment, not argv (argv is visible in `ps`). The
panel writes one file per site, `/etc/prepress/<site-id>.env`, mode `0600`, owned by root:

```bash
HOST=127.0.0.1
PORT=8101
PREPRESS_DATA=/home/acme/prepress/example.com
PREPRESS_OUT=/home/acme/htdocs/example.com
PREPRESS_SITE_URL=https://example.com
PREPRESS_PASSWORD=<generated by the panel, ≥ 16 chars>
PREPRESS_MCP_TOKEN=<generated by the panel, 32+ random bytes, hex>   # optional
# ANTHROPIC_API_KEY=sk-ant-...      # enables the built-in AI generate/edit
# ANTHROPIC_MODEL=claude-sonnet-5-5
```

If `PREPRESS_PASSWORD` / `PREPRESS_MCP_TOKEN` are omitted, Prepress generates them
into `admin-password.txt` / `mcp-token.txt` in the data folder and the panel can
read them from there. Add `--no-mcp` to `ExecStart` to turn the AI endpoint off.

All options: `prepress --help`.

## 4. systemd unit

One template unit; the panel adds a drop-in per site for the user:

`/etc/systemd/system/prepress@.service`

```ini
[Unit]
Description=Prepress editor for %i
After=network.target

[Service]
EnvironmentFile=/etc/prepress/%i.env
ExecStart=/usr/local/bin/prepress
WorkingDirectory=/
Restart=on-failure
RestartSec=2
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=full
UMask=0022

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/prepress@example.com.service.d/user.conf`

```ini
[Service]
User=acme
Group=acme
```

```bash
systemctl daemon-reload
systemctl start prepress@example.com     # when the user clicks "Edit site"
systemctl stop prepress@example.com      # when done (site stays online)
systemctl enable prepress@example.com    # only if it should always run (e.g. for MCP)
```

Logs go to the journal: `journalctl -u prepress@example.com`. The first lines show
the editor URL, publish folder, deploy targets and MCP status.

## 5. Reverse proxy for the editor

Create `edit.example.com` as a TLS reverse proxy to the site's port. Required:

- **Pass the original `Host` header.** Prepress rejects state-changing requests whose
  `Origin` host differs from `Host`. nginx's default (`$proxy_host` = `127.0.0.1:8101`)
  breaks login and saving with `403 Cross-origin request refused`.
- **No buffering** for `/api/events` (SSE, live reload when an AI edits) and `/mcp`.
- **Body size ≥ 100 MB** (media uploads are capped at 50 MB, editor saves at 100 MB).
- Long read timeout (SSE connections stay open).

```nginx
server {
    listen 443 ssl http2;
    server_name edit.example.com;
    # ssl_certificate ... (panel-managed)

    client_max_body_size 100m;

    location / {
        proxy_pass http://127.0.0.1:8101;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
```

Only proxy over HTTPS. The admin password and session cookie must never travel in
plain HTTP.

When the process is stopped, the proxy returns 502. Show a "Start editor" page
from the panel instead (`error_page 502 = @prepress_stopped;`), or start the unit
before redirecting the user.

## 6. The live site vhost

A normal static vhost on the docroot. Clean URLs and the 404 page:

```nginx
root /home/acme/htdocs/example.com;
index index.html;
location / { try_files $uri $uri/ =404; }
error_page 404 /404.html;
```

Apache: `ErrorDocument 404 /404.html` (directory indexes already serve `/menu/` → `menu/index.html`).

The site must sit at the root of its domain (links are root-relative, like WordPress).

## 7. Panel ↔ Prepress contract

| Need | How |
|---|---|
| Is it up? | `GET http://127.0.0.1:<port>/api/health` → `200 {"server":true,...}` (no auth) |
| Open the editor | Redirect to `https://edit.example.com/?admin=1`. The user signs in with the site password (show it in the panel, or read it from the env file / `admin-password.txt`). |
| Change the password | Rewrite `PREPRESS_PASSWORD` in the env file, delete `<data>/sessions.json`, restart. |
| AI / MCP access | Endpoint `https://edit.example.com/mcp`, header `Authorization: Bearer <PREPRESS_MCP_TOKEN>`. Example: `claude mcp add --transport http prepress https://edit.example.com/mcp --header "Authorization: Bearer <token>"`. The token can edit and publish the site, so treat it like the password. |
| Publish without a browser | Through MCP (`publish_site`). There is no other headless publish trigger. |
| Copy the site to other servers | The user adds deploy targets in the editor (Site → Deploy): other folders on the box or SFTP with SSH keys. Prepress runs `sftp` as the site user, so keys live in `/home/acme/.ssh`. |
| Backup | Back up `--data`. The docroot can always be regenerated by Publish. |
| Delete the site | Stop and disable the unit, then remove the env file, drop-in, data folder and proxy vhost. |
| Upgrade | Replace `/usr/local/bin/prepress`, restart running units. Back up `--data` first. |

## 8. Provisioning sketch

```bash
#!/usr/bin/env bash
# provision-prepress <site-id> <user> <domain> <docroot> <port>
set -euo pipefail
SITE=$1 USER_=$2 DOMAIN=$3 DOCROOT=$4 PORT=$5
DATA=/home/$USER_/prepress/$DOMAIN

install -d -m 0700 -o "$USER_" -g "$USER_" "$DATA"
PASS=$(openssl rand -base64 18)
TOKEN=$(openssl rand -hex 32)

install -d -m 0755 /etc/prepress
umask 077
cat > /etc/prepress/$SITE.env <<EOF
HOST=127.0.0.1
PORT=$PORT
PREPRESS_DATA=$DATA
PREPRESS_OUT=$DOCROOT
PREPRESS_SITE_URL=https://$DOMAIN
PREPRESS_PASSWORD=$PASS
PREPRESS_MCP_TOKEN=$TOKEN
EOF

install -d /etc/systemd/system/prepress@$SITE.service.d
printf '[Service]\nUser=%s\nGroup=%s\n' "$USER_" "$USER_" > /etc/systemd/system/prepress@$SITE.service.d/user.conf
systemctl daemon-reload
systemctl start prepress@$SITE
curl -fsS "http://127.0.0.1:$PORT/api/health" >/dev/null && echo "editor up on $PORT"
# then: create the edit.$DOMAIN proxy vhost (section 5) and store $PASS / $TOKEN in the panel DB
```

## Not built yet (candidates for the Exopanel integration)

- **Panel single sign-on.** Today the user types the site password. A signed,
  short-lived login link issued by the panel (shared secret in the env file)
  would let "Edit site" open the editor already signed in.
- **Idle shutdown.** Prepress doesn't exit by itself. A `--idle-exit <minutes>`
  flag, or the panel stopping the unit when there have been no requests, would save memory.
- **Path-prefix hosting** (`panel.example.com/sites/42/editor/`) needs a
  base-path option. Until then use one hostname per editor.
- **FTP deploy targets.** Only local folders and SFTP (keys) are supported.
